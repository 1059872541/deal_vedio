## 0. 一句话

> 我对它说一次「做我的世界 2026-06 的合集三、合集四」，之后它自己找目录、自己跑；该我动手时它告诉我，我做了什么不需要回报给它。

## 1. 人的动作就是信号

系统里**没有审批门**，也不需要你回报"我审过了"。原因：

- 你**不会没审字幕就花 45 分钟导出** —— 所以「导出启动」这一个可观测事实，本身就证明了「剪辑完成 + 字幕审完」
- 反过来，如果建一张 `approvals` 表，就得靠人回报；人一忘，数据就是假的。**假数据比没数据更坏**

| 人工动作 | 耗时 | 系统怎么知道你做完了 |
|---|---|---|
| 剪映里的创作剪辑 | 15 min | 不观测。素材达标即"剪辑中" |
| 字幕审查 | 5 min | **不单独记** —— 由「导出启动」反证 |
| 成片抽检（可选） | 5 min | 不可观测，也不阻塞任何环节 → **不建模** |

**原则：动作即意图；不为不可观测的事实建表。**

系统只做两件事：**看**（从文件系统推导状态）、**建议**（告诉你下一步可以干什么）。动手时机由你定。

## 2. 目录约定（唯一真相）

```
D:\VedioRecords\工作区\
└── {游戏}-{批次}\                       # 例：我的世界-2026-06
    ├── game.yaml                        # 项目配置（见 §3）
    ├── 素材库\                          # 批次级：打招呼语音、混剪原料（可选）
    │   ├── 合集1-3-目标-语音.mkv
    │   ├── 合集4-5-目标-语音.mkv
    │   ├── 2026-06-mc-合集687-混剪.mp4
    │   ├── 片头打招呼-纯净-声音.mkv
    │   ├── 片尾拜拜语音.mkv
    │   └── 开始吧-语音.mkv
    ├── 片头\                            # 成品片头（拼接时直接用），按合集组命名
    │   └── 2026-06-MC-开头-合集-1-3.mp4
    ├── 片尾\                            # 成品片尾
    │   └── 2026-06-MC-结尾.mp4
    ├── 术语库\                          # 该游戏的 ASR 易错词
    ├── log\                            # 本批次运行日志（人类可读）
    ├── 台账.xlsx                        # 批次级台账
    └── 合集\
        └── 合集三\
            ├── 素材\                    # OBS 原始录屏
            ├── 剪辑\                    # 剪映草稿、2h 导出、srt、corrected.txt
            ├── 标题.md                  # 数据中枢（集号 + 标题），人可读可改
            └── 成片\                    # 20 个成片

D:\VedioRecords\工作区\.vedio\
└── tasks.db                            # 全局状态库（含 游戏 / 批次 列）
```

### 2.1 目录语义

| 目录 | 级别 | 放什么 | 谁写 | 谁读 |
|---|---|---|---|---|
| `素材库/` | 批次 | 剪辑用的**原料堆**：打招呼语音、混剪片段、片头片尾招呼素材 | 人 | **程序不读**，仅人剪辑时取用 |
| `片头/` `片尾/` | 批次 | **已合成**的成品片头片尾 | 人 | `splice` |
| `术语库/` | 批次 | ASR 易错词表 | 人 | `correct` |
| `log/` | 批次 | 运行日志 | 执行体 | 人 |
| `合集/合集X/素材/` | 合集 | 本合集 OBS 原始录屏 | 人 / OBS | `balance`、`edit` |
| `合集/合集X/剪辑/` | 合集 | 草稿、2h 导出、`.txt`、`.srt`、`corrected.txt` | 剪映 / 执行体 | 执行体 |
| `合集/合集X/标题.md` | 合集 | 20 条标题 | `correct` | `rename`、`ledger` |
| `合集/合集X/成片/` | 合集 | 20 个成片 | `splice` / `rename` | `ledger`、`upload` |
| `台账.xlsx` | 批次 | 交付台账 | `ledger` | 人 / 对接方 |

### 2.2 片头 = 合集组级别

片头不是"一个游戏一个片头"，也不是"一个合集一个片头"，而是**几个合集共用一套**（1-3 / 4-5 / 6-7-8 / 9-10）。

**程序只认一件事：`片头/` 下的成品文件路径。** 成品是怎么来的（OP 素材 + 混剪 + 打招呼，在剪映里合成）是剪辑时的人才关心的事，不进数据模型。

所以：

- `素材库/` = 原料，程序不读
- `片头/` = 成品，程序只读这个
- `game.yaml` 的 `intro_mapping` = 合集 → 成品文件，允许多个合集指向同一个文件

## 3. 配置：公共规则 + 批次配置（两层，不合并）

### 3.1 模型

三份文件，两次使用：

| | 文件 | 作用 | 谁读 |
|---|---|---|---|
| **公共规则** | `conf/默认规则.yaml` | 全项目通用默认值：导出参数、时长、集数、命名模板、网盘路径模板 | **只有 `init` 读** |
| **游戏 diff** | `conf/游戏规则/{游戏}.yaml` | **只写与默认不同的键**。特殊游戏才需要建，一般没有 | **只有 `init` 读** |
| **批次快照** | `{游戏}-{批次}/game.yaml` | 本批次的**完整**配置，合并 + 问答后生成 | **运行时只读它** |

```
init:  默认规则(完整) ─┐
                       ├─深合并→ 模板 ─问答→ game.yaml（完整快照）
       游戏规则(diff) ─┘

run :                        game.yaml  ◀── 唯一输入
```

**关键：合并不发生在运行时。** 运行时只有 `game.yaml` 一份，不存在「先读 A 再被 B 覆盖」的层叠。

### 3.2 为什么这样更好

| | 层叠合并 | 实例化快照（本方案） |
|---|---|---|
| 运行时读几份 | 多份，按优先级覆盖 | **1 份** |
| 排查「为什么是 6 分钟」 | 要逐层找 | 打开 `game.yaml` 就有 |
| 甲方改规则 | 老批次行为跟着变（危险） | 老批次不动，新批次用新值（**可复现**） |
| 非技术用户 | 要理解多层继承 | 只看一个文件 |

### 3.3 游戏 diff：逐键覆盖，整份合并后使用

```
模板 = deep_merge(conf/默认规则.yaml, conf/游戏规则/{游戏}.yaml 若存在)
       # 逐键递归；标量后者覆盖前者；列表整体替换（不追加）
```

- **只写 diff**：一般游戏不建这个文件（"特殊录制规则很少见"）
- **不写 diff = 完全用公共规则**
- **写了 diff = 只有列出的键被覆盖**，其余沿用默认

因为 diff 文件本身不完整，**合并后必须做完整性校验**：键集要与 `默认规则.yaml` 一致，缺键直接报错，不允许"静默取默认"。

> 备注：合并只发生在 `init`。批次建好后 `game.yaml` 是完整快照，之后改 diff 文件**不会**影响已存在的批次。

### 3.4 公共规则（`conf/默认规则.yaml`）

它就是 `game.yaml` 的模板，每个字段都带默认值。

> **机器相关的东西不在这里** —— ffmpeg 路径、工作区根目录、剪映草稿目录、
> API key 的变量名，全在 `conf/本机.yaml`（**不进 git**，每台机器一份）。
> 这样业务规则能多人共享，机器各自管各自的。

```yaml
# ── 导出（剪映导出面板 5 项）──
export:
  resolution: 1080P
  bitrate: 推荐
  codec: H.264
  format: mp4
  framerate: 30fps
  timeout_seconds: 10800
  pause_between: 10

# ── 时长（单位：秒）──
duration:
  material_per_collection: 7200   # 每合集素材目标 2 小时
  episode_body: 360               # 每集正文 6 分钟
  episode_count: 20               # 每合集集数

# ── 命名 ──
naming:
  collection: "{host}之{game} {subtitle}"   # 中间只能一个空格
  episode: "第{cn_ep}集 {title}"            # 一个空格 + 约 5 个字
  file: "{collection} {episode}.mp4"

# ── 网盘 ──
netdisk:
  path: "/{month}/{host}/{game}/{collection}"
```

### 3.5 批次配置（`{游戏}-{批次}/game.yaml`）

由公共规则实例化，**所有字段都写全**（不是只写差异）：

```yaml
game: 我的世界
batch: 2026-06
collections: 10

# 以下三块在创建批次时问清楚，值来自公共规则或你的修改
export:
  resolution: 1080P
  bitrate: 推荐
  codec: H.264
  format: mp4
  framerate: 30fps
  timeout_seconds: 10800
  pause_between: 10

duration:
  material_per_collection: 9000   # 我的世界 2.5h，不是默认 2h
  episode_body: 450               # 我的世界 7:30，不是默认 6min
  episode_count: 20

naming:
  collection: "波波之我的世界 {subtitle}"
  episode: "第{cn_ep}集 {title}"
  file: "{collection} {episode}.mp4"

netdisk:
  path: "/{month}/波波/我的世界/{collection}"

# ── 本批次特有 ──
meta:
  host: 波波
  category: 端游          # 台账「类别」列取这个值
  year: 2026

templates:
  intro_mapping:
    default: 片头/2026-06-MC-开头-合集-1-3.mp4
    合集九: 片头/2026-06-MC-9-10-开头.mp4
  outro: 片尾/2026-06-MC-结尾.mp4

collection_names:        # 剪辑完成后填，用于重命名与台账
  合集一: 收集强力变身-上篇
  合集三: 收集强力变身-下篇

terminology:
  hotwords: 术语库/愚者整合包.md
subtitle:
  prompt_profile: 愚者整合包
```

### 3.6 `init` 就是「把问题问清楚」

创建批次目录时必须走这一步，问完即写完整 `game.yaml`：

```
📋 依据 conf/默认规则.yaml
1. 游戏？              我的世界
2. 批次？              2026-06（默认本月）
3. 建几个合集？        10
4. 每合集素材目标？    2h → 2.5h          ← 改
5. 每集正文时长？      6min → 7:30        ← 改
6. 每合集集数？        20
7. 导出参数？          1080P / 30fps / H.264 / mp4   ← 通常不改
8. 命名模板？          {主播}之{游戏} {副标题}        ← 通常不改
9. 片头片尾？          （本批次必填）
```

- 默认值全部来自公共规则（或游戏规则）
- 你只改真正不同的那几项
- **非技术用户**：agent 把问题连同默认值一起摆出来，回车即用
- **熟练用户**：`vedio init --game 我的世界 --batch 2026-06 --yes`

**这一步之后，「这个批次怎么干」就完全定死了，只在这一个文件里。**

### 3.7 文件内容边界

| 该进 `game.yaml` | 不该进 |
|---|---|
| 每个批次**可能不同**的值（时长、集数、导出参数、命名、网盘路径） | 程序**怎么做**（ffmpeg 用哪个编码器、重试几次、并发多少） |
| 本批次特有的映射（片头尾、发布名） | 目录结构本身（那是约定，写在代码里） |
| 你**会想改**的东西 | 只有调试时才动的开关 |

**一句话：配置管「做成什么样」，代码管「怎么做」。**

## 4. 真相在文件系统，DB 只是索引

**文件系统是唯一真相。** DB 不存"阶段"——阶段随时能从文件推导；存了必然出现「DB 说完成、文件却没了」的分裂。

DB 只存三样文件系统表达不了的东西：

| 表 | 存什么 | 为什么文件替代不了 |
|---|---|---|
| `events` | 动作时间线：何时启动导出、耗时多久、为什么失败 | 文件里没有「开始过」和「失败了」这两个事实 |
| `ledger_members` | 哪个合集已写进哪一份台账 | 一份 Excel 含多个合集，**看文件数判断不了「合集三进没进」** |
| `cache` | ffprobe 时长缓存（按 路径+size+mtime 失效） | 纯性能优化，删了也能跑 |

```sql
CREATE TABLE events (
  id INTEGER PRIMARY KEY, ts TEXT NOT NULL,
  game TEXT, batch TEXT, collection TEXT, ep_no INTEGER,
  stage TEXT NOT NULL,          -- material/clip/subtitle/export/splice/rename/ledger
  action TEXT NOT NULL,         -- start / done / fail / retry
  duration_ms INTEGER,
  detail TEXT                   -- 失败原因、改动条数、导出参数
);

CREATE TABLE ledger_members (
  id INTEGER PRIMARY KEY,
  game TEXT, batch TEXT, collection TEXT,
  ledger_file TEXT NOT NULL,    -- 台账-2026-06-上半.xlsx
  written_at TEXT NOT NULL
);

CREATE TABLE cache (
  path TEXT PRIMARY KEY, size INTEGER, mtime INTEGER, duration REAL
);
```

**`status` 的算法不是查表，是对账：**

```
扫描文件系统 → 推导物理状态
      ↓
叠加 events（导出启动过没、上次为什么失败）
      ↓
输出；若「文件事实」与「事件记录」矛盾，打 ⚠ 并把矛盾说出来
```

这样三种情况都能被看见：文件在但没记账、记了账但文件没了、两边都没有。

## 5. 状态判定规则（全部读文件系统）

| 状态 | 判定条件 |
|---|---|
| **素材** | `素材/` 下所有视频总时长 ≥ 目标。未达标时显示 `32m/2h` |
| **剪辑** | 素材达标 → 进入「剪辑中」（主要靠人，系统只看不干预） |
| **字幕** | `剪辑/*_corrected.srt` 存在 → 打勾。它是剪辑完成的**前置条件**，不是独立阶段 |
| **导出** | ① `events` 有 `export start` → **剪辑视为完成**（你定的规则）；② `剪辑/` 下出现 ≥目标时长的单文件（如 `26-06-MC-合集一.mp4`）→ 导出完成 |
| **拼接** | `成片/` 下视频数 ≈ 集数 |
| **命名** | `成片/` 文件名能与 `标题.md` 每条标题匹配（**与拼接共用同一次目录扫描**） |
| **台账** | 查 `ledger_members`：该合集是否已写入某份台账（不看 Excel 文件数） |

> 上传：**暂缓**，不在判定范围。

### 5.1 命令与人的动作

系统不阻塞、不等待。命令只在需要时被调用，前提由状态自然满足：

| 谁动手 | 命令 | 前提 |
|---|---|---|
| 人 | 剪映里创作剪辑 | 素材达标 |
| agent | `vedio asr` | 剪映里已点过字幕识别 |
| agent | `vedio correct` → `vedio apply-srt` | 剪映导出了 `.srt` |
| 人 | 剪映里导入 `_corrected.srt` + **审查** | `_corrected.srt` 存在 |
| agent | `vedio export` | 人审完（动作即信号，不另记） |
| agent | `vedio splice` | 导出完成 |
| agent | `vedio rename` / `vedio ledger` | 拼接完成 |

### 5.2 `init` 是创建批次目录的必经环节

详见 §3.6。要点：

- 读模板（有游戏规则用游戏规则，否则用 `conf/默认规则.yaml`）
- 把 9 个问题连同默认值一起问清楚
- **写完整 `game.yaml`** —— 所有字段都落盘，不留「靠继承」的字段
- 之后运行时只读这一个文件

| 角色 | 怎么走 |
|---|---|
| 非技术用户 | agent 把问题和默认值摆出来，回车即用 |
| 熟练用户 | `vedio init --game 我的世界 --batch 2026-06 --yes` |
| 甲方改规则 | 改 `conf/默认规则.yaml`（影响**新**批次）；已建批次不受影响 |

### 5.3 夜间无人值守

因为不阻塞，夜间流程就是一条顺序命令：

```
vedio run --game 我的世界 --batch 2026-06 --collections 合集三,合集四 \
          --steps asr,correct,apply-srt,export,splice,rename,ledger
```

- 按顺序对每个合集跑
- 某一步失败 → 记 `events.fail`、跳过该合集、继续下一个，**不整体中断**
- 第二天 `vedio status` 一眼看出哪些失败、为什么

## 6. `AGENTS.md` 要点（草稿）

给 agent 读，也给人读。核心是让它知道**什么时候该提醒人**，而不是"等谁批准"。

```markdown
# 视频处理项目

## 你的角色
你是这条产线的执行者。控制流由 `vedio` 命令行决定，你负责：
1. 把人话翻译成一条 `vedio run ...` 命令
2. 告诉人下一步该做什么、为什么（例如"合集三素材才 32 分钟，还得录"）
3. 任务结束后汇报结果（成功哪些、失败哪些、为什么）

## 绝对不要做
- 不要自己拼路径（用 `vedio paths --json` 拿）
- 不要在人没审字幕前启动导出
- 不要修改 `素材/` 里的任何文件

## 目录
{见本文件 §2}

## 状态判定
{见本文件 §5}

## 出错时
读 `vedio status --json` 的 `error` 列，用中文解释给人听，
给出「重试 / 跳过 / 停下来」三个选项，不要自己决定。
```
