# 安装与配置

> 给用户和助手都适用。**装一次就够**，之后日常看 [AGENTS.md](../AGENTS.md)。

## 首次引导（每个新用户 / 每台新电脑一次）

按顺序做，每一步都用一句人话告诉用户在干什么。

### 1.1 只检查两样东西

```powershell
python --version
where.exe ffmpeg
```

| 缺什么       | 你怎么做（**不要让用户自己折腾**）                                                                                                                          |
| ------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Python 3.12+ | 帮他用 `winget install Python.Python.3.12` 或官网安装，装完复验 `python --version`                                                                          |
| ffmpeg       | 下载 Windows 版解压到 `D:\softwares\ffmpeg`，把 `bin` 加进用户 PATH（`setx PATH "%PATH%;D:\softwares\ffmpeg\bin"`），**重开终端**后 `where.exe ffmpeg` 复验 |

### 1.2 装依赖

```powershell
python -m venv .venv
.venv\Scripts\pip install -r src/requirements.txt
```

### 1.3 问三个问题

#### **问题一：工作区放哪？**

```
你的视频工作区想放在哪个目录？
所有合集的文件夹都会建在它下面。（例如 D:\VedioRecords\工作区）
```

#### **问题二：剪映草稿目录在哪？**

> **不用问用户，也不用全盘搜。** 剪映自己维护一份明文索引，直接读它。

```powershell
Get-Content "$env:LOCALAPPDATA\JianyingPro\User Data\Projects\com.lveditor.draft\root_meta_info.json" -Raw -Encoding UTF8
```

里面的 `all_draft_store[].draft_root_path` 就是当前生效的草稿根，`draft_name` 是界面上显示的草稿名。

读出来之后，用一句话跟用户确认：「我找到你的草稿目录了，里面有 `MC-合集一`、`MC-合集二` 两个草稿，对吗？」

**不要全盘搜 `draft_content.json`** —— 会搜到用户以前用过的旧草稿根（实测搜到过一份三个月前的，6 个废弃草稿全在里面）。索引里的才是当前生效的。

#### **主播的名称**
问“主播名称是什么?” 让用户输入。更新到 `conf/默认规则.yaml` 下面的host。所以涉及主播名称的值,都从 naming:host 取值，忽略注释或者文档中提到的内容。
```yaml
naming:
  host: "波波"
```

### 1.4 回填 `conf/本机.yaml`

**只需要填一个值**：

```yaml
workspace:
  root: "用户选的目录"
```

`jianying.draft_dir` **留空就行** —— 程序会自动读剪映索引发现草稿根。只有自动发现不准时才手填。

然后把结果用一段话告诉用户：环境好了，可以开始了。

> `conf/本机.yaml` 不进 git。换电脑就重走一遍 §1。

### 1.5 回填 `conf/agent.yaml`（字幕涉及才需要）

要跑 `vedio subtitle` 才需要它。模板是 `conf/agent.example.yaml`：

```yaml
deepseek:
  api_key: "sk-..."
  model: "deepseek-flash"
  max_tokens: 98304
```

三个用途（构建知识库 / 字幕纠错 / 标题生成）**共用一个模型**。
模型名放这里而不是代码里，是因为它会随厂商更新而变；改名只改这一行。

**`max_tokens` 给少了会静默失败**，这是实际踩过的坑：
模型先输出 `reasoning_content`（内部推理），再输出 `content`（正文）。
额度被推理吃光时 `content` 是空的、`finish_reason=length` ——
表现是"跑了几分钟，字幕一处没改"。

实测数据（`deepseek-flash`，走生产同一条链路）：

| 素材               | 行号文件            | prompt | completion | 结果                                 |
| ------------------ | ------------------- | ------ | ---------- | ------------------------------------ |
| 21 分钟            | 8,711 B / 329 行    | 5,378  | 12,381     | 106 秒，stop                         |
| **2 小时（真实）** | 38,574 B / 1,552 行 | 14,035 | **34,482** | 231 秒，stop                         |
| —                  | max_tokens=8192     | —      | —          | 必死：推理吃光，正文 0 字，55 秒白跑 |

**completion ≈ 2.5 × prompt**，两档都成立（2.30 / 2.46）——
所以按 prompt 体量就能估出需要多少额度，代码里的开跑前预检用的就是这个比例。

`98304` 是 2 小时实测需求的 **2.85 倍**，按同比例可覆盖到约 5 小时素材。
想更早失败、少等一会儿可以调成 `65536`（≈1.9 倍）；两个值都不会多花钱 ——
`max_tokens` 是**上限不是预留**，模型说完就停，按实际用量计费。

> 三个坑要记住：
> ① 模型名有效 ≠ 能用。先拿 10 行字幕试，别拿整批试。
> ② 只用环境变量 `DEEPSEEK_MODEL` 临时换模型可以，但 `max_tokens` 要跟着调。
> ③ 代码会在开跑前按 prompt 体量预估额度，不够就 `[WARNING]` —— 别忽略它。
>    （它会把 32768 判为不够，而 2 小时实测确实要 34,482。）

**要估算"这段素材要花多少 token / 多久"，查 `docs/字幕规模与token参考.md`** ——
里面有实测样本、换算公式（时长 → 行数 → 字节 → token → 耗时）和一张查表。
