# 流水线现状

> 本文记录 **2026-11 时点上，一个人做一批视频实际要走的每一步**（AS-IS）。
> 目标形态见 [`目标架构.md`](目标架构.md)（TO-BE）。两文冲突时以 `目标架构.md` 为准。
>
> 本文的作用：它是"要自动化什么"的需求基线。每次流程有变化，先改这里。

---

## 0. 一句话

流水线**能跑通**，但每一步之间靠**人搬运**：

- 脚本不知道自己在哪个批次、哪个合集里，**要人告诉它目录**
- 目录约定写在本仓库文档里，**20 个脚本中 18 个不读它**
- 同一个仓库里同时存在 **3 套互不兼容的目录布局**
- 20 个能力中只有 **1 个**（`balance.py`）是真正可组合、可测试的原子能力

结果：人不是在做判断，人在**当路径的搬运工**。

## 2. 时间账：人在哪，机器在哪

| 项 | 每合集耗时 | 构成 |
|---|---|---|
| **人在操作** | **≈12 min** | 检查首尾 1 + 音轨 5 + 审字幕 5 + 查剪辑元素 1 |
| **人在等待** | ≈15 min | 字幕识别（可离开，但要回来） |
| **机器在跑** | **≈60 min** | 导出 45 + 切分拼接 ~15 |
| **录制** | 2–3 h | 与其它环节串行，无法压缩 |

**目标**：墙钟时间 ≈ 导出时间，可以过夜无人值守。人在白天只做那 12 分钟的判断。

## 3. 两个根本问题

### 3.1 问题一：目录约定只存在于文档里，程序查不到它

`目标架构.md` §2 那棵目录树，对 20 个脚本中的 18 个**是不存在的**。

#### 证据 1：三套目录布局同时活着

| 代 | 形态 | 还在用的脚本 |
|---|---|---|
| ① 初稿时代 | `D:\VedioRecords\剪辑草稿\初剪辑\{游戏}\{合集}\` | `title/update_title.py` |
| ② 无批次时代 | `D:\VedioRecords\工作区\{游戏}\合集\{合集}\`（**没有批次层**） | `title/get_videos_duration.py`、`deal_video_agent/monitor_subtitle.py` |
| ③ 当前约定 | `D:\VedioRecords\工作区\{游戏}-{批次}\合集\{合集}\{素材,剪辑,成片}` | `jianying_export/export_draft.py`、`splice_vedio/auto_splice_mp4.py`、`deal_video_agent/subtitle_agent.py` |

**4 个脚本指向已废弃的布局，3 个指向当前布局但把路径写死在模块级常量或 config 字典里。** 只有 `init`（`new_project_01_AI_USE.py`）按约定建目录。

#### 证据 2：`game.yaml` 是死文件

| 角色 | 是谁 |
|---|---|
| 写它 | `new_project_01_AI_USE.py`（1 个） |
| 读它 | `util/balance.py`（1 个，只读了 `duration` 的 2 个字段） |
| 无视它 | 其余 **18 个** |

`game.yaml` 里的 `collections` / `naming` / `netdisk` / `templates` / `meta` —— **没有任何脚本读**。

一个只有 1 个消费者的配置文件不是约定，是笔记。

#### 证据 3：约定里的东西从来没被生成过

`目标架构.md` §2 规定 `合集/合集X/标题.md` 是"数据中枢（集号 + 标题）"。实际：

| 检查 | 结果 |
|---|---|
| `D:\VedioRecords\工作区` 下 `标题.md` 的数量 | **0** |
| 标题实际写到哪 | `src/deal_video_agent/titles/{游戏}-{批次}_titles.md` |
| 那个目录在 git 里吗 | **在**（`我的世界-2026-06_titles.md`、`足球在线4-2026-06_titles.md` 均被跟踪） |

**用户的业务数据被写进代码仓库，并进入 git。** 它会跟着 `git clean` / `git checkout` / 换电脑一起消失。`knowledge_base/` 下 8 个 `.md` 同理。

#### 代价：48 个人工搬运点

| 类型 | 数量 | 分布 |
|---|---|---|
| `input()` 等键盘 | **24 处** | `rename_videos.py` 12、`new_project_01_AI_USE.py` 6、`subtitle_agent.py` 3、其余 3 |
| 模块级写死绝对路径 | **9 个脚本** | 见证据 1 |
| 要改 config 字典才能换目标 | **2 处** | `export_draft.py` 的 `output_path`、`auto_splice_mp4.py` 的 `WATCH_DIRS` |

这 48 个点的共同点：**它们要的信息，程序本来能自己查出来**（查文件系统 + 查 `game.yaml`）。

#### 附带后果：批次这一级在代码里不存在

- 目录约定有 `{游戏}-{批次}` 这一层
- `game.yaml` 有 `collections`、`naming`、`netdisk`
- 但**没有任何脚本以"批次"为单位工作**，它们都以"一个目录"为单位

所以「这个批次做到哪了」这个问题，**今天没有任何代码能回答**，只能靠人扫目录。

### 3.2 问题二：能力不是原子化的

判据（六条，缺一不可）：单一失败点 / 输入全从参数来 / 输出结构化 / 错误可分支 / 幂等可重入 / 可独立测试。

两个典型反例：

| 脚本 | 行数 | 违反了什么 |
|---|---|---|
| `splice_vedio/auto_splice_mp4.py` | **1536** | 监听 + 算切点 + 切分 + 编码器择优 + 并发 + 元数据 + 清理 全焊在一起。任何一个环节失败，只能整段重跑 |
| `.claude/.../rename_videos.py` | **685** | 检测 + 建议前缀 + 12 处 `input()` + 重命名 + 备份。既是能力又是 UI |

按"单一失败点"拆，`auto_splice_mp4.py` 其实是 3 个能力：

```
splice_probe  读每个成片/长片的时长        会因文件损坏失败
splice_plan   算切点（纯函数，不该失败）
splice_run    切分 + 拼片头片尾 + 校验片头  会因磁盘/关键帧/缺片头失败
```

### 3.3 这两个问题是同一个根

> **原子化的前提是「参数是任务，不是路径」。**

- 每个能力自带一套路径逻辑 → 它们对"合集一在哪"的理解不一致 → **不可组合** → 不是原子能力，只是小一点的脚本
- 反过来，一旦所有能力只收 `(游戏, 批次, 合集)`，路径由**一个函数**推导 → 三套布局归一（解决问题一），每个能力只关心自己那一步的业务参数（解决问题二）

缺的那一层叫 **任务身份**：`任务 = (游戏, 批次, 合集, 阶段)`。

## 7. 外部命名：人的命名，程序的标识

有一类名字**是人的命名，程序推导不出来**：

| 名字 | 实际长什么样 | 谁起 |
|---|---|---|
| 剪映草稿名 | `MC-合集-9`、`MC-合集10`、`MC-合集-8-9-混剪`、`MC-合集6-7 混剪`、`MC-开头模板`、`合集10-混剪` | 人，随手起 |
| 片头片尾文件名 | `2026-06-MC-开头-合集-1-3.mp4`、`2026-06-MC-结尾.mp4` | 人 |
| 合集副标题 | `波波之我的世界 通关极光城堡` | 人，剪辑完成后才定 |

上表第一行是 2026-11 对 `D:\VedioRecords\JianyingPro Drafts` 的**实地盘点结果**：6 个草稿、**5 种命名风格** —— 前缀有 `MC-` 也有没有的，分隔符有 `-` 也有空格的，编号有 `9` 也有 `10`，还混着「混剪」「开头模板」这种非正片草稿。

**结论：不解析名字。** 任何"从草稿名推断合集"的做法都不可靠，都会在某个批次上翻车。

### 7.1 但候选清单可以不开剪映就拿到

剪映 6.x 的草稿就是 `jianying.draft_dir` 下的一个文件夹，**文件夹名 = 剪映首页上显示的名字**，里面必有 `draft_content.json`。

```
列候选 = listdir(draft_dir) → 只保留含 draft_content.json 的子目录
```

秒级、不开剪映、凌晨也能跑。GUI 只在**点导出按钮**那一刻才需要。

### 7.2 做法：列候选 → 问一次 → 登记下来

| 步 | 动作 |
|---|---|
| 1 | 读 `draft_dir`，列出所有草稿名 |
| 2 | 给用户看候选 + 建议（「合集一 → `MC-合集一`？」） |
| 3 | 人指认一次 |
| 4 | **写入登记表**，之后免问 |

第 4 步不是为了省事，是为了**夜间无人值守**：导出若在凌晨 3 点失败重试，没有人醒着确认草稿名。**凡是"迟绑定的人为决策"，都必须落盘。**

### 7.3 登记表放哪：`合集清单.yaml`（批次根），不塞进 `game.yaml`

| 理由 | 说明 |
|---|---|
| **注释会被抹掉** | `game.yaml` 带大量注释，人要靠注释手改它。PyYAML 往返读写会丢注释，而登记表必须由程序反复写 |
| **写入方不同** | `game.yaml` 只由 `init` 写一次；登记表由程序边跑边追加 |
| **语义不同** | `game.yaml` = **规则**（建批次时定）；登记表 = **事实**（做完才知道） |

```yaml
# 合集清单.yaml —— 由程序维护，人只核对不手改
drafts:
  合集一: "MC-合集一"
  合集二: "MC-合集二"

templates:
  intro_mapping:
    合集一: "片头/2026-06-MC-开头-合集-1-3.mp4"
    default: "片头/2026-06-MC-开头-合集-1-3.mp4"
  outro: "片尾/2026-06-MC-结尾.mp4"

collection_names:
  合集一: "波波之我的世界 通关极光城堡"
```

> 这样会把 `templates` 和 `collection_names` 从 `game.yaml` 挪过来（它们本来就是迟绑定的）。是否迁移见 §8。

### 7.4 名字变了怎么办

人在剪映里改草稿名是常事。所以每次导出前：

1. 登记的名字在 `draft_dir` 里找不到 → 报 `draft_not_found`
2. 列出当前所有草稿
3. 让人重新指认 → 覆盖登记

**不许**用"最像的那个"自动顶上。猜错 = 导出一个错误的合集，45 分钟后才发现。

### 7.5 建议的命名约定（写进 AGENTS.md 当提示，不当契约）

```
{游戏缩写}-{合集中文}        例：MC-合集一
```

- 不用 `01` 这种纯数字：`MC-合集一` 和 `MC-01` 混在一批里就分不清了
- 同一批次内必须唯一
- 非正片草稿（混剪、开头模板）不要带 `合集` 字样，免得混进候选

**提示时机两处**：`init` 结束时说一次（成本为零）；第一次导出时让人指认（这一次免不了）。

**这是建议，不是契约。程序不解析草稿名，只查登记表。**

### 7.6 标题与副标题：批次级单文件（我之前的设想是错的）

我原先以为「每个合集一个 `合集X/标题.md`」。**不对。** 实际是**一个批次一个文件**，因为它要承担跨合集去重。

真实现状（`我的世界-2026-06_titles.md`，232 行）：

```markdown
# 我的世界系列视频标题列表
公共前缀:波波之我的世界
---
#### 合集一:收集强力变身-上篇
林中小屋初探
骷髅头颅之谜
…（20 行，无序号）
---
#### 合集二:收集强力变身-中篇
…
```

三样东西都在这个文件里：

| 内容 | 位置 | 谁写 |
|---|---|---|
| 公共前缀（`{主播}之{游戏}`） | 第 2 行 | `init` |
| 每合集的**副标题** | `#### 合集X:{副标题}` | `plan`（见 §7.7） |
| 每集 20 条标题 | 每节正文 | `correct` |

去重靠 `subtitle_correction.yaml` 里 `title_generation` 的 `{existing_titles}` —— 生成合集二时把合集一已有的标题喂回提示词，要求"不能和已有标题完全重复"。

**所以文件必须在批次级**：生成合集二时要读到合集一的标题，放在 `合集X/` 下反而要读 N 个文件、还要自己拼。

**唯一要改的是位置**：现在写在 `src/deal_video_agent/titles/`（代码仓库里、被 git 跟踪），应移到 `{批次}/标题.md`。

### 7.7 副标题能不能生成？—— 能，规则比想象的硬

真实数据里 10 个合集的副标题是 4 个「篇」：

| 篇名 | 覆盖合集 | 上下中 |
|---|---|---|
| 收集强力变身 | 合集一 / 二 / 三 | 上 / 中 / 下 |
| 下界合金升级 | 合集四 / 五 | 上 / 下 |
| 击败末影龙 | 合集六 / 七 / 八 | 上 / 中 / 下 |
| 初探巨龙 | 合集九 / 十 | 上 / 下 |

**规律：1–3 个合集组成一篇，篇内分上（中）下。** 和你说的一致。

生成只要三个要素：

| 要素 | 怎么来 |
|---|---|
| **分组**（哪几个合集一篇） | LLM 从这些合集的标题内容聚类推断 |
| **篇名**（4–8 字） | LLM 从该组 40–60 条标题里概括主题 |
| **上 / 中 / 下** | 按组内合集顺序自动 |

**时机**：必须等该组的标题都生成完才有料可依。所以它是**批次级、可重跑**的一步（`vedio plan`），不是每合集一步。

**"提前说好"的作用**：如果你在 `init` 时就声明「这批 10 个合集分 4 篇，篇内 3/2/3/2」，分组就不用 LLM 猜，只让它起名，准确率高很多。没声明就让它提案，人确认。

**风险要说清**：篇名是门面，定错了要改**文件名 + 台账 + 网盘目录**三处。所以只能是「**提案 + 人确认**」，不能全自动。

## 9. 批处理：两个正交维度

「全流程」和「从中间开始」是同一套能力的两种用法，不是两套流程。

| 维度 | 用法 | 例子 |
|---|---|---|
| **流程位置** | 从 `init` 开始走到底，或从任意环节切入 | 全流程 / 只做「导出+拼接+台账」 |
| **合集范围** | 一个合集，或本批次任意多个 | 只跑合集三 / 三个合集一起跑 |

**做法：每个 verb 都独立、幂等、接受 `--collections`。** 不设"总控脚本"，因为没有总控才可能从中间开始。

```
# 只匀素材，三个合集一起
vedio balance --game 我的世界 --batch 2026-11 --collections 合集一,合集二,合集三 --apply

# 只做后半段，三个合集一起
vedio run --game 我的世界 --batch 2026-11 --collections 合集一,合集二,合集三 \
          --steps export,splice,rename,ledger
```

**前提不是"上一步刚跑过"，而是"状态满足"。** 所以从中间开始天然成立：

| verb | 前提（看文件/登记，不看历史） |
|---|---|
| `export` | 草稿已在 `合集清单.yaml` 登记 + 人已审完字幕 |
| `splice` | `剪辑/` 下有 ≥目标时长的长片 + 片头片尾齐 |
| `rename` | `成片/` 有视频 + `标题.md` 里该合集有副标题 |
| `ledger` | 参与本次台账的合集都已完成拼接与命名 |

**顺序不是硬编码的链条，而是由文件状态自然约束的。** 这是「能从任意环节开始」的实现方式，也是「一个合集失败不拖累其它」的原因。
